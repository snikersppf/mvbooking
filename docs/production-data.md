# Production автомобили, тарифы и изображения

Реальные машины и цены вводит владелец бизнеса. Репозиторий не содержит
утверждённого production автопарка; прохождение unit-тестов не подтверждает
наличие этих данных. До заполнения и проверки каталог — blocker запуска.

## Заполнение через существующую админку

Использовать `/admin/vehicles` под ACTIVE MANAGER/ADMIN. Создание, изменение,
тарифы и изображения проходят существующие server validators, guards,
транзакции и AuditLog. Новый import/seed не нужен.

1. Создать автомобиль со статусом **UNAVAILABLE**: публичный каталог показывает
   только AVAILABLE. В форме по умолчанию AVAILABLE — обязательно сменить его
   перед первым сохранением, пока машина не подготовлена.
2. Указать уникальный slug, марку, модель, год, категорию, места, коробку,
   топливо, привод, залог, место получения. Проверить реальные значения,
   описание, двигатель и включение страховки. Валюта MVP — GEL.
3. Заполнить тарифы. Обычная сетка: 1–2, 3–6, 7–14, 15+ суток. Допустимы
   непрерывные диапазоны от 1, последний `maxDays = null`, без дыр/пересечений.
   Максимальная бронь — 365 суток; цены должны быть положительными после
   HALF_UP округления до 2 знаков. Сумма за весь период должна помещаться
   в `Decimal(12,2)`. Замена тарифов атомарна под блокировкой автомобиля.
4. Выбрать фотографии с компьютера, сохранить их, затем указать понятные alt
   и sortOrder. Проверить порядок и видимость на мобильном и большом экране.
5. Проверить условия аренды, страхование и залог с владельцем. Произвольное
   описание не меняет алгоритм расчёта. Сезонные цены, доплаты и специальные
   ограничения автоматически не рассчитываются: не обещать их пользователю
   как уже реализованные. Сначала согласовать отдельную бизнес-задачу.
6. Перевести машину в AVAILABLE, проверить её карточку и quote на 1, 2, 3,
   6, 7, 14, 15 и 365 суток. Сверить суммы с утверждённым прайсом.

Для вывода машины из продажи использовать UNAVAILABLE/MAINTENANCE. ARCHIVED
доступен ADMIN через архивирование; будущие активные брони запрещают операцию.
Изменение текущего тарифа не меняет сохранённые `pricePerDay`, `totalAmount`
и `depositAmount` прошлых бронирований.

## Хранение фотографий

Фотографии выбираются с компьютера в форме создания автомобиля или в разделе
изображений существующего автомобиля. Клиент отправляет `multipart/form-data`:
`payload` — JSON полей машины или списка сохраняемых фотографий, `files` — файлы.
Доступ только ACTIVE ADMIN/MANAGER с подтверждённой 2FA; действуют проверка
Origin, лимит операций и повторная проверка роли в транзакции.

Принимаются JPEG, PNG и WebP: проверяются MIME и сигнатура содержимого,
не только расширение имени. SVG/HTML не принимаются. Лимиты: 5 МиБ на файл,
10 файлов и 20 МиБ на запрос вместе с multipart-обрамлением, 30 фото на машину.
Полной перекодировки и удаления EXIF нет: не загружайте фото с личными данными.

Файлы сохраняются с UUID и расширением определённого формата в
`public/uploads/cars/`. В существующей модели `VehicleImage.url` сохраняется
только `/uploads/cars/<uuid>.<ext>`; миграция не нужна. Старые URL сохраняются
для совместимости. При ошибке записи БД новые файлы удаляются; повтор запроса
с тем же Idempotency-Key и содержимым возвращает сохранённый результат.
После аварийного завершения процесса могут остаться файлы без записей в БД.
Удаление фото из списка не удаляет его с диска; очистка таких файлов выполняется
оператором после проверки отсутствия ссылок и резервного копирования.

В production Compose каталог смонтирован в постоянный том `vehicle_uploads`.
Dockerfile создаёт каталог с правом записи для пользователя `node`. После
обновления соберите образ приложения и пересоздайте контейнер, а также
перезагрузите Caddy с новым конфигом: upload-маршрутам разрешено 20 МБ,
остальным запросам оставлен 1 МБ. Не используйте `docker compose down -v`:
эта команда удаляет данные томов.

Публичный GET `/uploads/cars/[filename]` обслуживает новые файлы без пересборки
Next.js; допускаются только сгенерированные имена, выставляются Content-Type,
`nosniff` и immutable cache. Каталог и оригинальное имя файла клиент не задаёт.
Пример вывода уже используется в `components/catalog/vehicle-card.tsx`:

```tsx
<img src={vehicle.image.url} alt={vehicle.image.alt ?? "Автомобиль"} width={640} height={360} />
```

Бэкап БД не содержит фотографий. Включите том `vehicle_uploads` в отдельное
резервное копирование и проверьте восстановление вместе с БД. Для нескольких
серверов нужен общий диск или отдельное объектное хранилище; локальные тома
разных серверов не синхронизируются. Serverless с эфемерным диском для этой
реализации не подходит.

## Read-only production data check

`npm run production:data:check` (`tsx scripts/check-production-data.ts`) читает
только явно переданный `DATABASE_URL`; `.env` скриптом не загружается. Для него
предпочтительна отдельная роль с SELECT на Vehicle, VehicleImage, PricingRule,
User. Использовать env процесса/production secret manager, не URL в argv.

`VEHICLE_IMAGE_ORIGIN` — origin принадлежащего проекту HTTPS CDN, без пути,
query и port. Эта переменная нужна **только audit CLI**; она не меняет
публичный API и не устанавливает runtime allowlist. Production audit также
принимает сгенерированные приложением пути `/uploads/cars/<uuid>.<ext>`.
Другие local и HTTP URL для разработки остаются допустимы в API; audit их
помечает. Наличие файлов на диске проверяется отдельно. URL с credentials, control characters и backslash отклоняются в
форме и API одинаково.

Команда не делает записи, seed, миграции, загрузку картинок или HTTP/DNS
проверки. Она проверяет наличие AVAILABLE автомобилей, обязательные поля,
полноту тарифов, фактический booking calculator для всех 1..365 суток,
валюту, наличие изображений на указанном origin и известные seed/test
маркеры пользователей/машин. Вывод — counts, коды ошибок и vehicleId;
email, пароли, URL с токенами, PII клиентов и connection strings не выводятся.
Exit code 1 означает ошибки данных либо невозможность выполнить проверку.

Это проверка снимка, а не блокировка изменения каталога. Повторять после
наполнения и изменения тарифов/картинок. Зелёный отчёт не подтверждает
право владения доменом, доступность файлов или реальность бизнес-данных.
Произвольную тестовую запись без известных маркеров обнаружить автоматически
нельзя: владелец также проверяет все автомобили и учетные записи вручную.

## Booking readiness и границы проверки

Каталог и quote используют Prisma-записи, не seed constants. Создание брони
повторно читает статус/тарифы внутри ReadCommitted транзакции: User lock →
Vehicle lock → Booking locks; лимит PENDING считается под User lock.
Exclusion constraint `booking_no_active_overlap` защищает базу при гонках;
соседние `[start,end)` периоды разрешены. Idempotency-Key + requestHash
возвращают ту же бронь при повторе неизменного запроса. Бронь, AuditLog и
outbox Notification сохраняются одной транзакцией; внешняя отправка относится
к worker, не к транзакции. Существующие integration-тесты покрывают двойную
бронь, интервалы, снимок цены, идемпотентность и отмену.

Обязательный launch acceptance: на изолированной `_test` БД и настроенных
каналах пройти регистрацию, quote, создание, replay, гонку двух запросов,
аккаунт клиента, подтверждение менеджером и отправку worker. На production
согласовать один реальный smoke сценарий с владельцем, без выдуманных клиентов
и автоматического seed. До успешного live acceptance и проверки реальных
данных эти пункты остаются **NOT VERIFIED / BLOCKER**.

Mock provider classes остаются для unit-тестов/абстракций; наличие их файла
не означает подключение к booking. Платежи исключены из MVP. Декоративные
изображения главной из `public/design` не являются записями автопарка и
должны иметь подтвержденные права использования. Тексты маркетинга и условия
аренды проверяет владелец перед запуском.
