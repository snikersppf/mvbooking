# Спецификация MVP MVBooking

Статус: исходное техническое задание. Детальный план до реализации — [architecture.md](architecture.md). При расхождении технических решений сначала согласовать план; не менять бизнес-код до его утверждения.

Создай MVP платформы аренды автомобилей в Грузии.

Важно: дизайнер еще не закончил работу. Не разрабатывай финальный визуальный стиль, брендинг или сложную UI-концепцию. Сейчас нужен функциональный технический MVP с нейтральным временным интерфейсом, который позже можно будет заменить без переписывания бизнес-логики.

## Цель MVP

Создать рабочую основу сервиса, которая позволяет:

- хранить автомобили;
- показывать каталог;
- проверять доступность автомобилей;
- создавать бронирования;
- регистрировать пользователей;
- разделять роли пользователей;
- управлять автомобилями и бронированиями через админскую часть;
- подготовить интеграции с оплатой, картами и уведомлениями;
- развернуть проект и проверить его тестами.

## Технологический стек

Используй:

- Next.js с App Router;
- TypeScript;
- PostgreSQL;
- Prisma ORM;
- Auth.js для авторизации;
- REST API через Next.js Route Handlers;
- Zod для валидации;
- React Hook Form для временных административных форм;
- Vitest или Jest для unit-тестов;
- Playwright для основных end-to-end тестов;
- Docker Compose для локального запуска PostgreSQL;
- Tailwind CSS для нейтрального временного интерфейса.

Архитектура должна позволять в будущем заменить временный UI на финальный дизайн без изменения моделей данных, API и бизнес-логики.

## Архитектура проекта

Организуй проект по слоям:

- `app/` — страницы и API routes;
- `components/` — UI-компоненты;
- `server/` — серверная логика;
- `server/services/` — бизнес-сервисы;
- `server/repositories/` — работа с базой;
- `server/validators/` — схемы Zod;
- `lib/` — общие утилиты;
- `prisma/` — schema, migrations, seed;
- `tests/` — unit и integration tests;
- `e2e/` — Playwright-сценарии;
- `types/` — общие типы.

Не помещай бизнес-логику непосредственно в React-компоненты или страницы.

## Логика бронирования

Реализуй серверный сервис бронирования.

Он должен:

1. Проверять существование автомобиля.
2. Проверять статус автомобиля.
3. Проверять корректность дат.
4. Запрещать дату окончания раньше даты начала.
5. Рассчитывать количество дней.
6. Выбирать подходящий тариф.
7. Рассчитывать стоимость аренды.
8. Добавлять депозит.
9. Проверять пересечение с существующими активными бронированиями.
10. Не допускать двойного бронирования.
11. Создавать бронирование в транзакции.
12. Возвращать итоговую сумму и статус бронирования.

Используй UTC для хранения дат и явно учитывай часовой пояс Грузии при работе с датами.

Продумай защиту от race condition при одновременном бронировании одного автомобиля.

## API

Создай REST API с валидацией входных данных.

### Vehicles

- `GET /api/vehicles`
- `GET /api/vehicles/:slug`
- `POST /api/admin/vehicles`
- `PATCH /api/admin/vehicles/:id`
- `DELETE /api/admin/vehicles/:id`

Поддержи фильтры:

- категория;
- цена;
- количество мест;
- коробка передач;
- тип топлива;
- привод;
- статус.

Поддержи сортировку и пагинацию.

### Availability

- `GET /api/vehicles/:id/availability`
- `GET /api/availability`

Параметры:

- vehicleId;
- startDate;
- endDate.

### Bookings

- `POST /api/bookings`
- `GET /api/bookings`
- `GET /api/bookings/:id`
- `PATCH /api/bookings/:id/cancel`
- `PATCH /api/admin/bookings/:id/status`

Клиент должен видеть только свои бронирования. Менеджер и администратор могут видеть все бронирования согласно своим правам.

### Users

- `GET /api/admin/users`
- `PATCH /api/admin/users/:id/role`
- `PATCH /api/admin/users/:id/status`

## Авторизация

Реализуй:

- регистрацию;
- вход;
- выход;
- восстановление пароля через подготовленный сервис;
- получение текущего пользователя;
- защищенные серверные маршруты;
- middleware для проверки доступа;
- разграничение ролей.

На первом этапе можно использовать email/password. Архитектуру подготовь для добавления Google, Telegram или другого OAuth-провайдера.

Не храни пароли в открытом виде.

Секреты должны находиться только в `.env`.

Создай `.env.example` без реальных секретов.

## Админская часть

Создай временную функциональную админскую панель без финального дизайна.

Страницы:

- список автомобилей;
- создание автомобиля;
- редактирование автомобиля;
- изменение статуса автомобиля;
- список бронирований;
- просмотр бронирования;
- изменение статуса бронирования;
- список пользователей;
- изменение роли пользователя;
- просмотр базовых audit logs.

Используй обычные таблицы, поля, select, кнопки и формы.

Не трать время на сложные анимации, визуальные эффекты, фирменные цвета или финальную композицию.

## Интеграции

Подготовь абстракции и адаптеры для следующих интеграций.

### Оплата

Создай интерфейс:

```ts
interface PaymentProvider {
  createPayment(input: CreatePaymentInput): Promise<CreatePaymentResult>;
  getPaymentStatus(paymentId: string): Promise<PaymentStatus>;
  refundPayment(paymentId: string): Promise<void>;
}
```

Добавь тестовый mock-провайдер.
Подготовь структуру для подключения Stripe или другого провайдера без привязки бизнес-логики к конкретному сервису.

### Карты

Создай абстракцию для карт и мест получения автомобиля.
На первом этапе можно использовать обычные текстовые адреса и координаты.
Подготовь структуру для подключения Mapbox или Google Maps позже.

### Уведомления

Создай интерфейс:
```ts
interface NotificationProvider {
  send(input: NotificationInput): Promise<NotificationResult>;
}
```

Добавь mock-провайдер.
Подготовь отдельные адаптеры для:
- email;
- Telegram;
- SMS;
- WhatsApp.
При создании и изменении бронирования сохраняй notification events, даже если реальная отправка еще не подключена.

## Временный интерфейс

Создай только нейтральный функциональный UI:
- стандартная типографика;
- простая цветовая схема;
- базовые таблицы;
- обычные карточки;
- формы;
- кнопки;
- состояния загрузки;
- состояния ошибок;
- состояния пустых списков.
Не разрабатывай финальный дизайн и не принимай необратимые решения по визуальному стилю.
Компоненты должны быть переиспользуемыми и не зависеть от конкретной темы.

## Тестовые данные

Создай Prisma seed:
- минимум 12 автомобилей;
- минимум 3 категории;
- тарифы для каждого автомобиля;
- тестового администратора;
- тестового менеджера;
- тестового клиента;
- несколько тестовых бронирований.
Тестовые учетные данные укажи только в документации для локальной разработки и не используй в production.

## Тесты

Добавь unit-тесты для:
- расчета количества дней;
- выбора тарифа;
- расчета итоговой стоимости;
- проверки пересечения бронирований;
- проверки доступности автомобиля;
- проверки ролей;
- валидации форм;
- обработки дат.
Добавь integration-тесты для:
- создания бронирования;
- невозможности двойного бронирования;
- отмены бронирования;
- изменения статуса менеджером;
- запрета доступа клиента к чужому бронированию;
- запрета обычному клиенту использовать admin API.
Добавь Playwright E2E-сценарии:
1. Пользователь регистрируется.
2. Пользователь входит.
3. Пользователь выбирает автомобиль.
4. Проверяет доступность.
5. Создает бронирование.
6. Видит свое бронирование.
7. Менеджер входит в админскую часть.
8. Менеджер подтверждает бронирование.
9. Клиент видит обновленный статус.

## Безопасность

Учти:
- хеширование паролей;
- серверную проверку ролей;
- валидацию всех входных данных;
- защиту API от неавторизованных запросов;
- безопасную обработку ошибок;
- отсутствие секретов в репозитории;
- базовую защиту от CSRF;
- rate limiting для регистрации и входа;
- безопасное логирование без паролей и токенов;
- проверку прав на каждое изменение бронирования.

- какие команды нужно выполнить;

- typecheck;
- test;
- build;
